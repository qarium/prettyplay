# Юзабилити-решения prettyplay (ветка `more-usability`)

> Записано по итогам интервью technical discovery 08.09.2026. Статус: **принято**.
> Топик инициирован пятью проблемами юзабилити, сформулированными пользователем (PRD/TODO для топика не создавались). Факты о текущем поведении собраны по коду реализации суб-агентами. Каждая запись фиксирует факт решения и его «почему».

## Термины

- **«Красивый отказ»** — раннер показывает падение проверки как FAILED с короткой человекочитаемой причиной (шаг; ожидание против наблюдаемого), а не как ERROR с трейсбеком по внутренностям библиотеки.
- **«Объяснение отказа»** — вердикт LLM: что произошло на странице в момент падения шага и что делать инженеру. Отвечает на вопрос «понятно ли человеку»; классификация лечения (rot / product_defect / incurable) отвечает на вопрос «лечить ли». Разные вопросы, один словарь (ADR-2).
- **Терминальный отказ шага** — `ProductDefectError` или `IncurableStepError`, дошедшие до теста. `LlmUnavailableError` — инфраструктурный, объяснением не снабжается.
- **«Доскролл»** — программная прокрутка как часть сценария (к элементу, на величину, до конца страницы, внутри контейнера); не путать с авто-прокруткой Playwright при выполнении действий.
- **Канал браузера** — значение `chrome`/`msedge` настройки browser: запуск реально установленного браузера через механизм Playwright channel (движок остаётся хромиумным).

## ADR-1. ProductDefectError — ассерт; чистая поверхность отказа

`ProductDefectError` дополнительно наследует `AssertionError` (множественное наследование с базой `PrettyplayError`), сообщение начинается с причины, трейсбек сворачивается до библиотечной границы. Раннеры и интеграции ждут `AssertionError` от проверок (unittest различает failure/error; pytest иначе репрезентует чужое исключение), а фасад библиотеки frame­work-агностичен — плагин под конкретный раннер невозможен, поэтому выравнивание делается типом, не интеграцией.

**Рассмотренные альтернативы:** все три ошибки наследуют `AssertionError` — отклонено: неизлечимый шаг и недоступность LLM суть ошибки исполнения, а не проверки; плагин раннера — отклонено: нарушает архитектурное решение «без плагинов и интеграций»; оставить типы как есть — отклонено: «некрасиво» из проблемы пользователя остаётся.

**Следствия:** таксономия из трёх видов сохраняется; `except AssertionError` и `except PrettyplayError` у интеграторов работают одновременно.

## ADR-2. Единый вердикт на каждом терминальном отказе

Каждый терминальный отказ шага (`ProductDefectError`, `IncurableStepError`) завершается вердиктом «категория (где применимо) + объяснение + рекомендация», который целиком попадает в сообщение исключения, в новое событие хуков (для отчётов интеграторов) и в лог. Объяснение строится по свежему состоянию страницы (снапшот; скриншот — при включённом `send_screenshots`); при недоступности LLM объяснение тихо пропускается с предупреждением в лог — основной отказ не искажается и не задерживается. Один механизм вместо двух: на путях, где классификация уже есть (лечение), вердикт переиспользуется; на путях без неё — запрашивается.

**Рассмотренные альтернативы:** отдельный «объяснительный» запрос параллельно классификации — отклонён: два словаря и лишние вызовы; объяснение только в лог/хуки без исключения — отклонено: объяснение нужно на месте падения, которое видит инженер.

**Следствия:** чинятся две потери сегодняшней реализации — `recommendation` не доходит до `ProductDefectError` на пути лечения; вердикт классификации теряется целиком при исчерпании лечения после rot.

## ADR-3. Провал проверки новой генерации — останавливать ретраи и классифицировать

Когда код кандидата при генерации исполняется, но проверка не сходится (Playwright `expect_*` поднимает `AssertionError` — типово отличимо от «элемент не найден»), ретраи останавливаются и шаг уходит на классификацию LLM: вердикт `product_defect` поднимает `ProductDefectError` с объяснением. Сегодня первый прогон законно падающей проверки сжигает бюджет генерации (по умолчанию 3 попытки, каждая — LLM-запрос) и падает как `IncurableStepError` — «ценность прогона» (реальный дефект) маскируется под неизлечимый шаг, а классификация на этом пути не вызывается вовсе.

**Рассмотренные альтернативы:** поднимать `ProductDefectError` сразу без LLM — отклонено: теряется объяснение, расходится с ADR-2; сохранять статус-кво ретраев — отклонён: маскировка дефекта.

**Следствия:** не-`AssertionError`-ошибки кандидатов ретраятся как сегодня; дополнительный LLM-запрос возникает только когда проверка реально пала.

## ADR-4. Скриншоты в руках автора теста — получить и сохранить

Основной объект получает две способности: получить PNG-байты текущего состояния и сохранить PNG-файл по явно указанному пользователем пути (`filepath/filename.png`); привязки к конкретному каталогу нет — путь выбирает пользователь. Снимок — всей страницы (full-page, единообразно с фасадом). Автоскриншотов при терминальном падении шага нет — решение снимать остаётся за пользователем (явно отклонено на интервью).

**Рассмотренные альтернативы:** один метод с необязательным сохранением — отклонён пользователем в пользу двух простых; автосохранение при падении в каталог по умолчанию — отклонено: решение за пользователем.

**Следствия:** библиотека впервые пишет артефакт по произвольному пути пользователя; каталог кеша остаётся единственным собственным следом на диске.

## ADR-5. Настройка headless и каналы chrome/msedge; переименование env

Появляется настройка `headless` (в `[tool.prettyplay]`, по умолчанию `true` — текущее поведение; env `PRETTYPLAY_BROWSER_HEADLESS`), а допустимые значения `browser` расширяются до `{chromium, firefox, webkit, chrome, msedge}`: последние два — Playwright channel, запускающий установленный браузер, т.е. существующий у пользователя `browser = "chrome"` начинает работать. Env-переменная браузера переименована чисто: `PRETTYPLAY_BROWSER` → `PRETTYPLAY_BROWSER_NAME`, старое имя перестаёт действовать (внешних потребителей нет; при встрече старого имени — подсказка нового). Сегодня headless в `launch()` вовсе не передаётся (headless — умолчание Playwright), а `browser = "chrome"` падает невалидным значением.

**Следствия:** TOML-ключ остаётся `browser` — переименована только env-переменная; для `chrome`/`msedge` требуется установленный локально браузер, при его отсутствии — действенное сообщение (см. ADR-6).

## ADR-6. Действенные ошибки конфигурации

Ошибки валидации настроек оборачиваются в громкую действенную ошибку библиотеки: имя настройки, полученное значение, список допустимых значений. Документация конфигурации это уже обещает («невалидное значение — громкая действенная ошибка с именем настройки»), а реализация выдаёт сырой `pydantic.ValidationError`; это та же поверхность «настройка просто не работает» из проблемы пользователя про браузер.

## ADR-7. Доскроллы — в фасаде страницы

Фасад страницы расширяется скрол-способностями: страничные — прокрутка к элементу, прокрутка на величину вниз/вверх, прокрутка до конца/начала страницы; контейнерные (карусели) — подвод элемента в зону видимости внутри прокручиваемого контейнера и прокрутка контейнера на величину. Покрывает пользовательские сценарии, которые сегодня невыразимы: в поверхности фасада скролла нет вообще, авто-прокрутка Playwright срабатывает только при действиях. Примитивы установленного Playwright 1.62 достаточны: `scroll_into_view_if_needed`, `mouse.wheel`, `evaluate`/`window.scrollTo`.

**Ограничения:** фасад — контракт обратной совместимости: только расширение, без переименований и удалений; перечень API страницы для LLM — зашитая в движке строка, зеркалящая `.usages/facade.md`, — меняется только вместе с ним (иначе модель не увидит новых возможностей); скролл — поверхность сгенерированного кода шагов (предложения вида «доскроллить вниз»), отдельного API уровня основного объекта для скролла не появляется.

**Нерешённое (будущее):** «крутить до появления» (бесконечная лента: прокручивать, пока не появится элемент) — отложено вне топика; частично собирается повтором «до конца» + ожиданием элемента.

## Сводка интервью

Пять проблем пользователя → решения: «некрасивый» отказ → ADR-1 + ADR-3; неиспользуемое преимущество LLM → ADR-2; скриншоты для отчётов → ADR-4; браузер «с головой» и `browser = chrome` → ADR-5 + ADR-6; доскроллы → ADR-7. Все решения приняты пользователем в трёх раундах файлового диалога (файлы `autonomous_execution.q1–q4` в каталоге стадии pipeline).
