# Технические решения prettyplay MVP (ветка `master`)

> Записано по итогам интервью technical discovery 26.08.2026. Статус: **принято**.
> Основано на PRD `.goga/history/2026/the-first-version/prd.md`. Каждая запись фиксирует сам факт решения и его «почему».

## Термины

- **Кеш-шаг** — сгенерированный исполнимый артефакт шага, хранящийся в репозитории и исполняемый без LLM.
- **`cache_key`** — обязательный явный контекстный ключ, задаваемый интегратором на основном объекте; входит в идентичность кеш-шага.
- **`cache_path`** — подкаталог внутри каталога кеша, часть адресации кеш-шага.
- **Основной объект** — объект, создаваемый интегратором на тест; владеет браузерным контекстом и адресацией кеша (пример пользователя: `PrettyTest('cache_key', cache_path=…)` — иллюстрация формы, не контракт).
- **Гниль / дефект продукта / неизлечимость** — таксономия из PRD (R14, R18, R19).

---

## ADR-1. Браузерный драйвер — Playwright

Продукт — обёртка над Playwright: его встроенные auto-wait прямо снижают главную боль PRD (хрупкость селекторов → «гниль»), a11y-снапшот даёт дешёвый структурированный контекст для LLM, sync- и async-API покрывают любые раннеры.

**Рассмотренные альтернативы:** Selenium — индустриальный стандарт, но без auto-wait (генерённый код сам управляет ожиданиями → больше ложной гнили) и без a11y-снапшота (LLM кормили бы сырым HTML); абстракция над несколькими драйверами — удваивает поверхность генерации/лечения в MVP и делает каждый кеш-шаг зависимым от драйвера. Обе отклонены для MVP.

**Следствия:** матрица браузеров MVP = {Chromium, Firefox, WebKit} (PRD оставлял её инженерным решением); `playwright` — жёсткая зависимость пакета.

## ADR-2. Исполнение — синхронное

MVP исполняется только через sync API: тесты pytest/unittest по умолчанию синхронны, R2 требует запуска стандартной командой раннера, интегратор не тащит event loop, кеш-код однороден.

**Нерешённое (будущее):** async-исполнение — явное расширение, не в MVP.

## ADR-3. Кеш-шаг = сгенерированный Python-код

Кеш хранит сгенерированный Python-код (функция фиксированной формы, работающая через фасад драйвера), а не декларативный IR: шаги вида «ввести логин и пароль» и проверки с ожиданиями требуют полноценного языка, а IR превратился бы в разработку второго языка с бесконечным расширением.

**Рассмотренные альтернативы:** декларативный IR/JSON (безопасно и валидируемо, но потолок выразительности), гибрид с жёстким валидатором подмножества Python.

**Следствия:** доверенная граница — сам репозиторий (запуск тестов и так исполняет произвольный код репо, кеш лежит в нём); код генерируется только через узкий фасад — это правило промпта генерации, не валидатор в MVP; git-диффы бесплатно дают ревизуемость лечения («полная магия» не страдает — инженер код не читает).

## ADR-4. Идентичность кеш-шага

Уникальный ключ шага = `cache_key` (обязательный явный параметр основного объекта) + тип шага (action/assertion) + hash нормализованного текста шага. Нормализация: Unicode NFC, trim, схлопывание пробелов, casefold («Нажать Войти» = «нажать войти»); перевод (RU/EN) — другой шаг; машинного перевода на пути кеша нет.

**Отклонено:** авто-вывод «контекста» из origin приложения и дефолтное значение cache_key — контекст задаёт интегратор явно; «существенно иной контекст» из R12 = другой `cache_key` → промах кеша → регенерация (не ошибка). Один и тот же текст как action и как assertion — разные шаги.

## ADR-5. Адресация и хранение кеша

Один `.py`-файл на шаг с метаданными (текст, cache_key, дата); имя файла — детерминированная функция ключа. `cache_path` — **часть адреса**: шаги живут в заданном подкаталоге, переиспользование — внутри одного подкаталога; по умолчанию (путь не задан) — общий корень, поэтому одинаковые `cache_key` переиспользуются между тестами (первая половина R12). Корень кеша по умолчанию — `<корень репозитория>/.prettyplay/cache/`, настраивается (`cache_root`).

**Отклонено:** трактовка `cache_path` как чисто организационной раскладки (адрес только из cache_key+текста) — создаёт неоднозначность хранения при одинаковых шагах в разных путях.

## ADR-6. LLM-интеграция — официальные OpenAI и Anthropic SDK

Поддерживаются два провайдера через официальные SDK `openai` и `anthropic`; все три зависимости (`playwright`, `openai`, `anthropic`) — жёсткие, из принципа «поставил и работает».

**Отклонено:** LiteLLM (тяжёлая зависимость и чужой слой абстракции поверх ключевой функции); вариант «свой тонкий протокол/интерфейс + extras» — отклонён пользователем в пользу жёстких зависимостей официальных SDK. Вендор-локина нет: код кеша не зависит от провайдера, LLM нужен только для генерации и лечения.

## ADR-7. Входы LLM при генерации и лечении

Модель получает: a11y-снапшот текущей страницы (Playwright ariaSnapshot — дёшево и стабильно, без HTML-шума), текст шага, тексты предыдущих шагов теста (сценарный контекст повышает качество составных шагов), при лечении — существующий код шага и ошибку. Скриншот — опциональный дополнительный вход, включается флагом на проект (`send_screenshots`).

**Отклонено для MVP:** сырой HTML как основной вход (шумно и дорого); скриншоты как обязательный вход.

## ADR-8. Итеративная генерация и бюджеты попыток

Генерация — ограниченный цикл: сгенерировать → исполнить → при ошибке вернуть ошибку и свежий снапшот → перегенерировать, ≤ **3** попыток. Лечение — ≤ **2** попыток перегенерации. Бюджет общий на шаг в рамках прогона (не сбрасывается между тестами — исключает бесконечные циклы при переиспользовании шага); настраивается в конфиге проекта; исчерпание любого бюджета = явный отказ «неизлечимо» (R15, критерий успеха 5).

## ADR-9. Кеш не инвалидидируется по версии библиотеки

Версия библиотеки не участвует в валидности кеш-шага (решение пользователя): в кеш-файлах нет версии формата, шаг не перегенерируется при апгрейде prettyplay.

**Следствие (ограничение):** фасад драйвера, против которого генерируется код шага, обязан сохранять обратную совместимость между версиями библиотеки — иначе старый кеш молча сломается; ломающие изменения фасада требуют миграционной стратегии.

## ADR-10. Параллельная запись в кеш — атомарная замена без блокировок

Запись во временный файл с уникальным именем (pid+random) в целевом подкаталоге, затем `os.replace()` поверх целевого файла: на POSIX атомарен; на Windows при занятом цели — короткий retry, затем отказ от записи конкретного шага с громким сообщением (прогон не падает). Гонка двух процессов на один шаг — побеждает последняя запись (оба варианта кода семантически эквивалентны: один ключ = один смысл шага).

**Отклонено:** файловые блокировки каталога — простои, риск зависших локов, новые отказы вместо устранения старых. Обоснование относительно замечания о конфликтах rename/move: конфликт исчерпывается уникальным tmp-именем + retry, изоляция подкаталогами (ADR-5) дополнительно сужает точки столкновения.

## ADR-11. Кеш в read-only средах (CI) — best-effort

Кеш читается всегда; запись выполняется только при доступном для записи каталоге. В read-only среде генерация/лечение работают «в памяти», результат прогона корректен, но несохранённый новый/вылеченный шаг громко помечается в выводе («не сохранено: кеш только для чтения»). Рабочий процесс команды: генерация локально → коммит кеша → CI исполняет полностью из кеша без LLM-ключей (критерий успеха 2). Отдельный «CI-режим» не вводится.

## ADR-12. Видимость шагов и лечения — logging + хуки

Тексты шагов (R7) и громкие сообщения о лечении (R17) идут через стандартный `logging` (логгер `prettyplay`) — раннеры и CI захватывают логи сами, отчётность не меняется (R2). Для интеграторов — тонкий интерфейс колбэков; собственная шина событий не вводится.

## ADR-13. Конфигурация проекта

Неизменяемая часть настроек — секция `[tool.prettyplay]` в `pyproject.toml`: браузер/драйвер, `model` (+ опциональные переопределения `generation_model` / `classification_model`), `base_url`, `cache_root`, бюджеты попыток, `send_screenshots`. Секреты (ключи LLM) — только из env-переменных, никогда в файле репозитория (в конфиге можно указать имя переменной); env-оверрайды всех настроек — для CI.

## ADR-14. Секреты и тест-данные в тексте шага — не поддержаны в MVP

Текст шага попадает в кеш, отчёты и запросы к LLM, поэтому секреты в шагах не поддержаны и это фиксируется как документированное ограничение (решение пользователя). Подстановка env-переменных в текст шага рассматривалась и отклонена для MVP.

---

## Нерешённые вопросы / за рамками MVP

- **Async-исполнение** — единственное крупное расширение модели исполнения (ADR-2).
- **Абстракция над драйверами** (например, Selenium) — не тянуть, пока не появится реальный спрос.
- **Секреты/тест-данные в шагах** — нужна схема вида подстановки env-переменных, если всплывёт в реальном использовании (ADR-14).
- **Ломающие изменения фасада генерации** — миграционная стратегия для существующего кеша (следствие ADR-9).
