# Расширение конфигурации prettyplay: per-test рантайм, PrettyConfig со слиянием, инструкции генерации, универсальные локаторы, remote-браузер

## Current State

Текущее состояние библиотеки (факты собраны на technical discovery по CODEMANIFEST клеток config / driver / engine / cache / корневого prettyplay):

1. **Конфиг не прокидывается в тест.** `PrettyTest(cache_key, cache_path)` настроек не принимает; всё разрешается процессным синглтоном `get_runtime()` → `PrettyplayRuntime` — один браузерный процесс, один LLM-провайдер, один реестр бюджетов на весь процесс.
2. **Бюджеты «на весь запуск».** `RunBudgets` живёт весь процесс; шаг, переиспользуемый N тестами, делит один бюджет попыток — задокументированный инвариант клетки cache.
3. **Нет пользовательских инструкций генерации.** Системный промпт генерации фиксирован (практика `generation_prompt` клетки engine); передать per-project стиль генерируемого кода («отдавай приоритет data-test-id») в запрос невозможно.
4. **Фасад ограничен тремя локаторами.** `find_by_role` / `find_by_label` / `find_by_text` — локации по data-атрибутам, CSS-селекторам и XPath нет; сгенерированный код не умеет искать по test-id.
5. **Только локальный браузер.** `DriverSession` всегда делает launch(); настройки `browser_endpoint` нет (раздел remote-подключения уже добавлен в практику playwright на стадии формулировки — код пока не следует практике).
6. **Программного переопределения настроек нет.** `load_config` читает pyproject+env; слияния с явно переданными значениями не существует.

## Description

Реализовать пять принятых решений ADR топика `additional-configuration` (`.goga/history/2026/additional-configuration/adr.md`) в существующих ячейках prettyplay — единый выпуск расширения конфигурации:

- **ADR-1. Per-test рантайм.** Каждый `PrettyTest` строит собственный рантайм: свой экземпляр конфигурации, свой браузерный процесс, свой провайдер, свои бюджеты попыток. Процессного синглтона больше нет; `get_runtime()` уходит из публичного контракта (внутренняя деталь фасада). Бюджеты попыток пер-тестовые — инвариант «бюджеты не сбрасываются между тестами» разворачивается. Каждый рантайм регистрирует свою остановку в atexit — все браузеры останавливаются к выходу процесса; ленивость сохраняется — конструирование `PrettyTest` дёшево, браузер стартует на первом шаге.
- **ADR-2. PrettyConfig — единая модель настроек и многослойное слияние.** `PrettyConfig` — публичное имя полной модели настроек (псевдоним `Config` клетки config), а не отдельный объект-подмножество. Переданный в `PrettyTest` конфиг задаёт только явно указанные значения; незаданные/пустые поля разрешаются многослойным слиянием против pyproject+env. Одна модель — одно место валидации; каждая новая настройка автоматически доступна во всей цепочке pyproject → env → `PrettyConfig`.
- **ADR-3. Настройка `generation_prompt` — пользовательские инструкции в запросы генерации.** Строковая настройка (env `PRETTYPLAY_GENERATION_PROMPT`, дефолт — пустая). Непустое значение попадает отдельным блоком **USER INSTRUCTIONS** в запросы генерации и регенерации (healing); фиксированный системный промпт не меняется; классификация отказов не затрагивается. В адрес кэша инструкции не входят: смена инструкций не инвалидирует кэш, кэшированный шаг не перегенерируется. Внутренняя практика движка `generation_prompt` переименовывается в `system_prompt`, освобождая термин для публичной настройки.
- **ADR-4. Фасад: универсальные локаторы.** Фасад страницы расширяется способностью локации по любым data-атрибутам, CSS-селекторам и XPath. Дефолтный приоритет системного промпта (role → text → label) не меняется — доступность остаётся глобальным дефолтом, приоритет подстраивается инструкциями пользователя per-project. Листинг поверхности API и facade-практика меняются синхронно — новые локаторы модель увидит автоматически.
- **ADR-5. Remote-исполнение через Playwright ws-эндпоинт.** Строковая настройка `browser_endpoint` (env `PRETTYPLAY_BROWSER_ENDPOINT`, дефолт — пустая = локальный запуск, как сегодня). Эндпоинт задан → драйвер подключается (Playwright connect) вместо запуска; `headless` игнорируется (видимость окна управляется сервером); `browser` по-прежнему выбирает тип двигателя для подключения. Эндпоинт-URL допустим в конфиге (адрес, не ключ); ротация в CI — через env-override. В связке с ADR-1 каждый тест может подключаться к своему эндпоинту.

### Целевая форма использования (примеры — форма, не контракт; имена фиксирует brainstorm)

```python
from prettyplay import PrettyTest, PrettyConfig

# per-test конфиг: явно заданное выигрывает, остальное разрешается из pyproject+env
test = PrettyTest(
    cache_key="login-flow",
    config=PrettyConfig(
        browser="firefox",
        generation_prompt="Отдавай приоритет data-test-id атрибутам",
        browser_endpoint="ws://ci-grid:3000/playwright/chromium",
    ),
)

with test as t:
    t.action("Открыть страницу логина")
    t.assertion("Форма логина видна")
```

```python
# новые локаторы фасада — доступны сгенерированному коду шагов
page.find_by_attribute("data-test-id", "submit-button")
page.find_by_css("form > button.primary")
page.find_by_xpath("//button[@type='submit']")
```

```toml
# pyproject.toml — те же настройки файлом
[tool.prettyplay]
generation_prompt = "Отдавай приоритет data-test-id атрибутам"
browser_endpoint = "ws://ci-grid:3000/playwright/chromium"
```

## Scope

**In scope:**

- `PrettyTest` принимает конфиг; каждый тест строит собственный рантайм (конфигурация, браузерный процесс, провайдер, бюджеты); `get_runtime()` упраздняется как публичный контракт (ADR-1)
- Пер-тестовые бюджеты попыток: сброс на каждый тест; защита от бесконечных ретраев в рамках теста (ADR-1)
- Atexit-остановка каждого рантайма: все браузеры останавливаются к выходу процесса; идемпотентность close (ADR-1)
- `PrettyConfig` — публичное имя модели `Config`; многослойное слияние: явно заданное выигрывает, незаданное/пустое падает на pyproject+env; единая валидация файловых и программных значений (ADR-2)
- Настройка `generation_prompt` (TOML + env `PRETTYPLAY_GENERATION_PROMPT`, дефолт пустая); блок USER INSTRUCTIONS в запросах генерации и регенерации (ADR-3)
- Переименование практики движка `generation_prompt` → `system_prompt` (ADR-3)
- Локаторы фасада по data-атрибутам, CSS, XPath + синхронное обновление листинга поверхности API в практике генерации (ADR-4)
- Настройка `browser_endpoint` (TOML + env `PRETTYPLAY_BROWSER_ENDPOINT`, дефолт пустая); connect вместо launch при заданном эндпоинте; `headless` игнорируется при connect (ADR-5)
- Обновление cell-level практик: `driver/.usages/facade.md`, `prettyplay/.usages/lifecycle.md`, `config/.usages/configuration.md`
- Обновление проектной практики playwright (remote-подключение) — применено на стадии формулировки
- Тесты по конвенциям проекта (`pytest`, `ruff`)

**Out of scope:**

- CDP-подключение (`connect_over_cdp` к запущенному Chrome с debugging-портом) — отложено как будущее расширение отдельным полем (ADR-5)
- Ключование рантаймов по эффективному конфигу (тесты с одинаковым конфигом делят один браузер) — отклонено (ADR-1)
- Приватный рантайм только при явно переданном конфиге — отклонено: одна семантика поведения (ADR-1)
- Участие хеша инструкций в адресе шага / инвалидация кэша от смены инструкций — отклонено (ADR-3)
- Инструкции в классификацию отказов и в адрес кэша — отклонено (ADR-3)
- Смена дефолтного приоритета локации системного промпта на test-id-first — отклонено: глобальный дефолт консервативен (ADR-4)
- Вклейка инструкций в системный промпт — отклонена (ADR-3)
- Дизайн контрактов (сигнатуры, изменения CODEMANIFEST) — стадия brainstorm

## Acceptance Criteria

- Два `PrettyTest` в одном процессе: каждый со своим браузерным процессом и своими бюджетами; результаты не зависят от порядка выполнения тестов
- Шаг, переиспользуемый N тестами, получает N×попыток за запуск: бюджеты сбрасываются на каждый тест; исчерпание бюджета внутри одного теста по-прежнему даёт `IncurableStepError`
- Все запущенные браузеры останавливаются к выходу процесса без явных close (atexit per-runtime); повторный close безопасен
- Конструирование `PrettyTest` не запускает браузер и не требует LLM-креденшелов; браузерный процесс стартует лениво на первом шаге теста
- `PrettyTest` без конфига работает как сегодня (pyproject+env); с конфигом: явно заданное значение выигрывает, незаданное/пустое разрешается из pyproject+env (проверить на `base_url`/`model`, заданных только в файле)
- `get_runtime()` отсутствует в публичном экспорте пакета; `PrettyConfig` доступен в публичном экспорте пакета (алиас полной модели `Config`)
- `[tool.prettyplay] generation_prompt` / env `PRETTYPLAY_GENERATION_PROMPT`: непустое значение → блок USER INSTRUCTIONS в запросах генерации и регенерации; пустое → запросы без блока; классификация без блока при любой настройке
- Смена инструкций не инвалидирует кэш: кэшированный шаг выполняется без перегенерации; инструкции видны только на свежей генерации
- Практика движка называется `system_prompt`; публичная настройка — `generation_prompt`; коллизии имён в манифесте нет
- Сгенерированный код умеет локейтить по data-атрибутам, CSS и XPath через фасад; листинг поверхности API в запросах содержит новые локаторы зеркально `facade.md`; дефолтный приоритет промпта role → text → label не изменился
- `browser_endpoint` задан → подключение по ws вместо локального запуска; пуст → локальный launch как сегодня; `headless` игнорируется при подключении; `browser` выбирает тип двигателя
- Обратная совместимость фасада: только расширение, без переименований и удалений; кэшированные шаги продолжают работать
- `ruff check` и `pytest tests/ -x` зелёные; Python 3.10+

## Risks and Constraints

- **Упразднение публичного `get_runtime()` — осознанный breaking change.** Внешних потребителей нет (факт discovery); интерактивные сессии, использующие `get_runtime().close()` из `lifecycle.md`, переходят на закрытие тестовых объектов — практику обновить в задаче
- **Цена per-test браузера:** ~секунда на запуск браузера на каждый тест — принятая цена решения об изоляции (ADR-1)
- **Atexit-накопление:** каждый рантайм регистрирует свою остановку — N тестов = N atexit-хуков; каждая остановка идемпотентна и безопасна при незапущенном состоянии
- **Драйверные потоки:** per-test рантайм → per-test драйверный поток; строго последовательное driving сохраняется в рамках каждого теста; интерактивные хосты (IPython/Jupyter) продолжают работать
- **Различение «явно заданного» от «незаданного»:** модель с пустыми дефолтами — пустое поле означает «взять из pyproject+env»; конвенция pydantic-моделей проекта (пустые дефолты, `None` только для явного отсутствия) делает различие механическим
- **Синхронность двух копий поверхности:** листинг API страницы зеркалит `driver/.usages/facade.md` — правятся только вместе, иначе модель не увидит новых локаторов
- **Коллизия имени `generation_prompt`** решается переименованием практики движка в `system_prompt` — до переименования одно имя делало бы две работы в одном манифесте
- **Remote-тесты:** реальный ws-эндпоинт в окружении тестов недоступен — моки внешних границ и `pytest.mark.skipif` по конвенциям проекта
- Python 3.10+; конвенции проекта (`conventions`) обязательны

## Scope Estimate

Одна задача (решение пользователя). Масштаб: 5 ADR, 6 ячеек, ~13 затрагиваемых типов — один архитектурный рефактор композиции (per-test рантайм) + точечные расширения. Разбиение отклонено: кластеры изменений плотно пересекаются по ячейкам (рантайм потребляет слияние; ADR-3/ADR-5 добавляют настройки в одну модель и один конструктор; ADR-3/ADR-4 меняют одну практику генерации) — подзадачи редактировали бы одни клетки параллельно и не несли самостоятельной ценности. Весь выпуск поставляется вместе в ветке `additional-configuration`. Следующая стадия (brainstorm) разнесёт контрактные правки по ячейкам.

## Existing Architecture

Затрагиваемые ячейки и характер изменений:

- `prettyplay` (корневой фасад) — `PrettyTest`: параметр конфигурации, собственный рантайм теста; `PrettyplayRuntime`: из процессного синглтона в per-test композицию; `get_runtime`: упраздняется как публичный контракт; `StepExecutor`: пер-тестовые бюджеты; обновление `.usages/lifecycle.md`
- `prettyplay/config` — `Config`: поля `generation_prompt`, `browser_endpoint`, публичный псевдоним `PrettyConfig`; `load_config`: многослойное слияние с явно переданными значениями; обновление `.usages/configuration.md`
- `prettyplay/driver` — `DriverSession`: жизненный цикл меняется с run-scoped на per-test (сессией владеет рантайм теста); глобальная аннотация клетки «один браузер на весь запуск» и правило фасад-практики «браузер общий на запуск» разворачиваются; connect по ws-эндпоинту при заданной настройке, локальный launch иначе; `open_context` остаётся источником изолированного контекста страницы; `PageFacade`/`LocatorFacade`: локаторы по data-атрибутам, CSS, XPath; обновление `.usages/facade.md`
- `prettyplay/engine` — практика `generation_prompt` переименовывается в `system_prompt`; блок USER INSTRUCTIONS в запросах генерации/регенерации; синхронное расширение листинга поверхности API
- `prettyplay/cache` — `RunBudgets`: семантика per-test, инвариант «бюджеты не сбрасываются между тестами» разворачивается; адресация кэша не меняется
- `prettyplay/llm` — `LlmProvider.generate_step_code` и обе реализации провайдеров (`OpenAiProvider`, `AnthropicProvider`): новый вход инструкций генерации в полном паритете — блок USER INSTRUCTIONS собирается в пользовательский контент запроса провайдерами, отдельного слота в фиксированном списке входов порта сегодня нет; `classify_failure` не меняется; `FailureClassification`, `create_provider` — без изменений
- `prettyplay/failures`, `prettyplay/reporting` — не затрагиваются
