# Project rules

## Bounded upstream mirroring

The real third-party API at the mirrored interaction level is the sole source of truth for which facade members exist and what they are called: invented facade-only names, and renames of the legacy surface made without checking what the upstream library actually provides, are rejected. New capabilities on the public facade ride the existing method names that mirror the underlying library's API, added as parameters following the library's own precedent and leaving current behavior unchanged; growing the surface with new non-mirror call families is rejected. Mirroring is scoped to the user-level interaction surface — upstream capabilities that mutate or observe state invisibly to the observable page-state model (script evaluation, network or protocol-level interception, tracing-style instrumentation) are permanently excluded, so the state model feeding failure classification and healing remains a truthful account of what step code did. Mirrored members reproduce the upstream framework's surface and semantics exactly: complete parameter sets with explicit "not applied" sentinels, matching member kind (property versus method), and stock failure modes whose existing classification stays untouched. A facade member that reads resource state keeps the natural, immediate, argument-less reading form of the underlying resource — a read-only property rather than a method signalling an internal crossing — preserving the idioms that generated code and practice documentation rely on. Known sharp edges are never smoothed over with custom guard logic inside the code; consumer guidance for them lives in the practice documentation.

## Single facade choke point

No raw object from the underlying library ever crosses the facade boundary: every exposed capability returns the project's own facade type so call chains stay composable, every object kind reachable from step code is wrapped in its own facade, and raw underlying driver objects — including values nested inside parameters — never leak out. Execution marshals through the facade's dedicated execution thread, preserving the framework's built-in auto-waiting semantics. Objects bound to that private event-loop thread are never handed to the calling thread, neither directly nor through a per-call marshaling proxy: the only sanctioned access is executing a caller-supplied callable wholly inside the owning thread, with plain data as the only thing allowed to cross back. The driver's marshaling boundary covers every facade kind uniformly, and the same boundary is the single attachment point for cross-cutting reactions: a reaction that must trigger whenever a given terminal error is raised on any of several paths is attached at exactly one boundary — the executing facade — rather than duplicated at every raise site, so one catch point provably covers every path and none can be missed. Internal runtime handles obey the same confinement from below: a handle exposes a small, fixed set of plumbing members and may never proxy, delegate, or re-export the underlying engine's capabilities — the handle is plumbing, not a managed surface, and delegation layers are rejected because they recreate the managed-surface problem one level down. The provider port plays the same role for LLM access: every new LLM-facing capability is added as an operation on the existing port, which stays the single point of SDK calls and the fixed multi-provider parity contract; the orchestration layer owns only the decision and retry logic and invokes the port — never building the request or parsing the model output itself — and generic pass-through port operations are rejected.

## Contained exception boundary

Raw third-party or validation-framework exceptions never escape the library boundary: they are wrapped in a library-defined error type that derives from the library's single root error, so one except clause catches every library failure. The wrapper carries a human-readable diagnostic rendered per offending item and chains the original exception as its cause. Errors extending the project's base error are declared in the DSL as mutations via the `::` syntax from the base type, not as independent types; the error base is declared in the manifest of the taxonomy-owning cell. Each distinct terminal failure mode receives its own named member in the taxonomy so it stays individually addressable; reusing an existing error kind for a new failure mode — overloading its meaning and hiding the new mode — is rejected.

## Loud failure over silent degradation

Invoking a capability before its precondition holds raises a loud, actionable failure telling the caller what to do first, rather than silently returning useless output; decisions that belong to the caller (such as when to capture artifacts) are never taken implicitly by the library, and explicit write operations surface their failures loudly. The same discipline governs user instructions: an unmet or inexpressible instruction must surface as an error and is never silently ignored. Every successfully executed candidate passes an independent compliance check before caching on all execution paths; only findings of blocking severity fail the attempt, with the violation text carried into the retry. An empty verdict means compliant, a malformed verdict is a hard failure with nothing cached, and zero check calls are made when the feature is off or no instructions were given. Budget exhaustion while a blocking violation stands becomes a terminal error naming the instruction.

## Failure payloads authored once at construction

Structured failure or diagnostic text that must reach multiple surfaces (exception message, log record, event payload, hook payload) is composed exactly once, at the moment the failure object is constructed, and all downstream consumers reuse that one render instead of each composing its own variant. The same compose-once rule governs every multi-part record destined for downstream contracts: it is composed in exactly one place and travels as pre-composed plain data that consumers display as-is, because introducing a structured cross-contract type that each consumer must render is rejected — it turns every consumer into a renderer and widens the surface for divergence. Data needed for programmatic recovery travels in a machine-readable field on the error, populated by the raiser; it is never reconstructed from the rendered human-readable text and never exposed through event or log payloads. The components orchestrating the failing flow construct the payload; the outcome types never request or build it themselves; it is carried as one optional field on terminal outcomes, and when the enrichment source is unavailable the value is simply absent — a quiet skip that never delays or blocks the failure. The render itself stays minimal and self-sufficient: it opens with its own failure classification — the terminal class name and the authored reason — continues with delimited labeled blocks for the failing step, its decomposed error headline and the recognized detail shapes, omits blocks that have no content, keeps verdict labels at column zero with two-space continuations, and excludes bulky context such as source code, which stays in the stores designed to hold it; the message therefore keeps its primary triage signal in every display context, including those that provide no outer prefix.

## Minimal generation-friendly surface growth

When the API is exercised by model-generated step text, the surface favors explicit, direction-named methods taking constrained positive-integer amounts over signed or encoded arguments, because a sign embedded in an argument is a source of generation errors and reads worse in generated propositions. The surface grows only when existing constructs cannot express the need: where exposed properties plus plain language-level assertions already express a check, no facade-specific expectation or convenience member is added. Growth is additive — existing call sites stay untouched — and every edit stays surgical, touching exactly the content the change requires: surviving mechanics stay verbatim, only the relevant section of a usage file grows, and a constants-only code change never inflates into a contract-signature change. When design variants satisfy the requirement equally, the one that keeps existing signatures and neighboring contracts untouched is chosen: introducing new cross-imported primitive types that force signature changes and drag unrelated contracts into the change scope is rejected. Auxiliary verification steps likewise ride infrastructure that already exists: they run on the effective model already used for the primary work rather than on a dedicated checker model, and their non-blocking findings surface through the existing library logger — no new hook or event types are introduced just to carry them. The library-level generation system prompt likewise carries only universal mechanics — notably that assertions go exclusively through the facade's expectation methods, never raw language-level asserts or SDK-style state reads — while locating strategy is owned entirely by each consuming project's own user-instruction channel. Every code-generation and regeneration request carries a dedicated reference of concrete call forms — a vocabulary, not a style guide and not an allowlist — so weak models can write correct code without relying on prior knowledge; the error-driven regeneration loop is a second line of defense, never a substitute for the vocabulary.

## Owner-dialog decision and approval authority

A direct owner answer given in free-form dialog is the strongest decision signal and overrides both the accepted task file and accepted decision records: the overridden work is excluded from scope, the affected acceptance criteria are removed and renumbered, the deviation from the prior artifacts is recorded explicitly, and the corrected artifact is re-presented for approval. A governing requirement discovered mid-pipeline is absorbed the moment it is flagged: the requirement is restated as a mandatory design property, the affected block is reformed around it, the recommendation is flipped if necessary, and the approval gate is re-asked — defending the original recommendation and compensating with a repair loop is rejected. All interactive communication with the user — gate questions, reports, options, narration, final summaries — is conducted in the human language the user has chosen, while every persistent project artifact stays in the single fixed artifact language; a language correction from the user is treated as a standing rule applied from the first question onward rather than a one-off remark, and after such a correction the rejected artifact is re-presented in the dialog language without losing any decision already taken. Nothing generated executes unseen: every candidate is shown in full and followed by an explicit approval prompt before execution; rejection aborts the turn without execution yet is recorded in history as a completed turn with its outcome, so rejected or failed candidates are never dropped and the model never re-proposes a blind candidate. Every executed turn ends with a definitive green-or-red outcome and a full untruncated record, interactive attempts consume no generation or healing budgets, and failed code is never re-executed in a loop nor are timing windows re-armed inside the dialog. Operational consequences that remain the owner's to handle at run time are captured in the plan's acceptance checks and non-code work items instead of being decided silently.

## Acyclic cell topology

New functionality owned by an existing component is placed in nested subcells under that owner rather than as new top-level cells or as plain types inside the owner, so each responsibility zone keeps its own cell, the owner stays homogeneous, and the top-level tree stays bounded. Knowledge-bearing logic stays with the cell that owns the knowledge it serves: parsing or decomposition logic lives in its owning cell as a pure routine with typed output that degrades gracefully to empty parts on unparseable input, consumers such as the shared render consume that output, and pre-existing pure formatting policies in other cells are left untouched, so template knowledge never spreads beyond its owner. Types needed by multiple cells (including the failure taxonomy for interrelated functions such as generation and healing) are extracted into a separate leaf cell imported by all consumers. Every dependency edge stays one-directional and acyclic under the schema: when a nested or consumed component must re-execute code that lives in its owning component, the owning code is handed in as a callable parameter instead of being imported, so the consumed component stays a pure policy with zero upward imports; mutual imports and cycles in the cell graph are not allowed.

## Logical-unit event semantics

Observable events fire per logical unit (once per step, or once per underlying model request) and never per internal execution retry; retries are visible only as log records, and every step lifecycle ends with exactly one closing event carrying the outcome, regardless of success or failure. Handling follows the same discipline: always-on ambient event routers are last-resort handlers that defer to in-step captures — handling claimed by the step's own code always wins — and the ambient router resolves only unclaimed events, exactly once each, in a deterministic order inside the owning thread; neither removing the ambient router nor letting it resolve events on arrival is acceptable.

## Self-contained current-state cell specifications

Contract and usage specifications describe only the present state of the system — what exists and how it behaves now — never narrating change history: no mentions of legacy names, renames, deprecated behavior, or what no longer works; a specification that references change history is reworked to describe the current state. Contracts also stay minimal: a contract declares only types with a live external role, and internal mechanics — including types whose sole purpose disappeared when generated code moved to the genuine API — are deleted from the contract outright rather than retained for internal wiring; internal wiring is not declared contractual. They are fully self-contained: CODEMANIFEST and usage files reference no external project documents (ADRs, PRDs, task files), and every requirement is stated inside manifest annotations so the cell contract is readable and verifiable without consulting source documents. Cross-artifact disciplines are given explicit anchors inside the consumer cells' contracts as placement-adjacent annotation lines, rather than living only in prose outside the contracts. Optional-parameter default values are written inside the signature itself in contracts and type tables, never left implicit in the surrounding prose; a signature whose default appears only in a description is considered defective and must be corrected. The observable-behavior contract (what the outside world must see) is specified on the type that carries it, while the mechanics that enforce that behavior are specified on the boundary methods that execute it — neither stated in both places nor left unspecified. Usage files are named after the functional domain they describe (not technical or abstract names); every cell carries, alongside conceptual descriptions, a usage file with ready code examples of calling its API, written in English only — sample data in any other natural language is not permitted — and the snippets demonstrate every facet of the public surface they document, including both commanding and verifying calls. Any modification to an already-approved fragment is re-approved as its own decision before work continues.

## Parity-first clean-break atomic landing

When a standing stability contract collides with parity, parity wins: a mirror member is renamed or removed only together with an upstream-level re-mapping, the old name simply stops acting, and breakage of previously cached consumers is accepted cost. The break stays pure — no backward-compatibility alias, no deprecation hint, no runtime warning directing users to the new name, no migration layer cushioning it. The change lands as one atomic change together with every artifact that describes or is generated from the surface — declarations, the contract manifest, cross-cell annotations and usage files, the machine-facing API listing and prompt, the configuration surface, and the published documentation — because a partial landing desynchronizes the real surface from what the code generator is told about it. Provider-bound surfaces exist as frozen local constants mirroring the practice files across several artifacts; any surface change updates the contract, the practice, every consumer's mirror constants, and the public documentation together in one iteration, and no mirror is ever read at runtime. A capability family reaches consumers through exactly one canonical idiom listing per consuming concern; duplicating the element-surface enumeration into additional documents is rejected as a second, drift-prone copy. Partial renames and artifacts that still carry a known-stale name are rejected, and the corrected change is re-issued for approval with the corrected form carried into all later work.

## Strict replay and classification discipline

Configuration-time validation covers only syntactic formats; semantics that depend on an external registry's vocabulary resolve in the driver at runtime against the live registry, so configuration never hardcodes a copy of a vocabulary it does not own. Strict mode never generates, heals, or consumes run budgets: a cache miss fails immediately, a failed cached step is only classified into its fixed error taxonomy, LLM availability is discovered by attempting the classification call itself (unavailability logs a warning and raises a step-type-determined error without a verdict), and no proactive provider probes are made. User-supplied classification instructions render as a clearly delimited block placed last in the user content, formatted identically for every provider, and appear only in classification requests — generation requests and caches stay unaffected.

## Stateless multi-target interaction

Working with several concurrently live targets (windows, tabs, frames) never introduces hidden session state such as an "active target" that silently redirects subsequent actions; moving between targets is an explicit operation invoked on the target's own facade.

## Empirical scratch-tree verification

Claims that rest on unexercised toolchain or DSL capabilities, and assembled plans whose manifests exist only as document snippets, are verified by materialization rather than by reading: build a minimal scratch project or apply the full plan to a scratch copy of the tree, run the lint and schema validators, propagate every surfaced defect back into the source document, and clean up the verification artifacts afterwards.

## Neutral defaults for new behavior settings

A newly introduced behavior-changing configuration setting defaults to the behavior that existed before the setting: the new behavior is strictly opt-in, and the outcomes of scenarios that no explicit setting touches are unchanged.
